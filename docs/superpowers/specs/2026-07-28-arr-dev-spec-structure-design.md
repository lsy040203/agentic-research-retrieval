# ARR 精简 DEV_SPEC 结构设计

## 目标

将 ARR 的 `DEV_SPEC.md` 提升为适合小规模项目的完整规格入口：既保留可执行的任务、依赖和验收条件，也记录每个已完成阶段的技术讲解与测试证据。

## 参考与适配原则

参考 `D:\agent_study\MODULAR-RAG-MCP-SERVER-main\DEV_SPEC.md` 的分层组织方式，但不复制其面向大型 RAG/MCP 平台的模块、供应商、Dashboard 或多模态章节。ARR 仅保留与科研记忆、检索决策和阶段交付直接相关的内容。

## 目标章节

1. 文档元信息与目录：版本、状态、权威设计、Python 环境和目录链接。
2. 项目概述与设计原则：科研 Agent 定位；作用域隔离、证据可追溯、安全非执行、先证据后决策。
3. 功能边界与阶段范围：已完成 P0/A1/A2、当前 B1、后续 C1-E1 和 V1 禁止项。
4. 技术架构与数据模型：ASCII 图、核心对象、独立数据库和旧 `MemoryRecord` 关联边界。
5. 模块与文件结构：已实现和计划文件的职责、输入和输出边界。
6. 测试与验收标准：单元、集成、E2E、安全和性能的阶段性验收标准。
7. 已完成阶段讲解与验收证据：每个完成阶段的目标、文件、字段/调用流、测试结果、限制和讲解文档链接。
8. 实施排期与依赖：状态、依赖、验收条件、阶段讲解入口。
9. 变更记录：日期、阶段、摘要、测试证据、讲解路径。
10. 未来范围：V1 外能力。

## 阶段收尾规则

每完成一个阶段，必须同时完成以下文档动作：

1. 在排期中更新阶段状态、依赖完成情况和实际测试证据。
2. 在“已完成阶段讲解与验收证据”中增加中文条目，说明目标、文件、核心字段/流程、限制和测试结果。
3. 在 `docs/superpowers/` 下增加或更新该阶段的中文讲解文档，并从 DEV_SPEC 链接。
4. 在变更记录中添加日期、阶段、摘要、验证命令和讲解路径。
5. 同步 auto-coder 引用文件；生成内容必须与 DEV_SPEC 的状态一致。

## 非目标

- 不把 B1-E1 未完成能力描述为已实现。
- 不把大型参考项目的 MCP、多模态、Dashboard 或远程提供者设计引入 ARR V1。
- 不修改业务代码、测试或数据库 schema。

## 验收

- 所有目标章节均存在，且内容与 ARR 已确认设计一致。
- P0/A1/A2 有独立讲解与可复核测试证据。
- B1-E1 清晰标记为未实现或计划中。
- 阶段收尾规则可以直接作为后续开发的固定检查清单。
